# Database Schema Review — Production Readiness

> SmartDroneInspection · FA26SE112 · Review before implementation
> Reviewed against: `database-production.plan.md`, `01-SYSTEM-SPECIFICATION.md`, `01-ARCHITECTURE-OVERVIEW.md`, and the official capstone register.

## 1. Review result

The original plan is a strong functional starting point, but it is not safe to implement verbatim as a production database. The implementation must use the decisions below.

### 1.1 Count correction

The plan says **27 tables**. The listed schema contains **29 tables**:

- Users/RBAC: 6
- Assets: 3
- Planning: 5
- Requests/Missions: 5
- Reports/Defects/Tickets: 7
- AI: 3

The requirements have six database modules, while the business scope has eight areas. The implementation tracks the 29 physical tables and maps them to the six database modules.

## 2. Decisions applied before coding

| Area | Original risk | Production decision |
|---|---|---|
| Tenant isolation | `organizations` exists, but assets have no organization boundary | Add `organization_id` to assets and enforce it in application queries. User organization remains nullable only for platform administrators. |
| Case-insensitive identity | Plain unique email/username allows `User@x` and `user@x` duplicates | Store normalized lowercase values and add unique indexes on `normalized_email` and `normalized_username`. Preserve original display values. |
| IDs and timestamps | Implicit defaults are not explicit | All entities use UUID keys generated by the application; all timestamps are UTC. Append-only events use their own event timestamp. |
| Text safety | No maximum lengths were specified | Apply explicit max lengths to identifiers, names, codes, MIME types, IP addresses, user agents, status strings and object keys. Long descriptions remain `TEXT`. |
| Coordinates | Latitude/longitude could contain impossible values | Add checks: latitude `-90..90`, longitude `-180..180`; require both or neither. Keep `DOUBLE PRECISION` for MVP because the official requirement only specifies PostgreSQL. |
| Money and measurements | Precision/range absent | Money uses `numeric(15,2)` and must be non-negative; confidence uses `numeric(5,4)` in `0..1`; percentages use `0..100`; durations/distances are non-negative. |
| Soft delete | Soft-deleted business rows could leak into normal reads | Add global query filters to `ISoftDelete` entities. Do not soft-delete append-only logs, refresh tokens, telemetry, or embeddings. |
| Audit | `old_values/new_values` can leak secrets | Audit writer must redact password hashes, tokens, API keys and sensitive credentials before JSONB persistence. Audit rows are append-only. |
| SmartDroneHub idempotency | External retries can create duplicate missions | Keep `mission_creation_key` unique and add an external mission ID unique partial index. Never use an external call without an idempotency key. |
| Mission/AI FK cycle | `mission_images.ai_analysis_job_id` plus `ai_analysis_jobs.mission_image_id` creates an unnecessary two-way relationship | Remove `mission_images.ai_analysis_job_id`. `ai_analysis_jobs.mission_image_id` is the single source of relationship. Add an index on it. |
| AI job target integrity | Three nullable target FKs allow ambiguous jobs | Add a database check requiring exactly one target (`mission_image_id`, `defect_id`, or `report_id`) for the supported job types. Application validation remains the first line. |
| Asset full-text search | A generated `tsvector` based on an array needs exact PostgreSQL expression/version handling | Use a stored `search_vector` column maintained by a database trigger (or a carefully tested generated expression). Add a GIN index. Do not rely on an untested generated expression. |
| Battery constraint | Plan references nonexistent `battery_percent` on `drone_missions` | Validate `max_battery_used_percent` on `drone_missions`; validate `battery_percent` on telemetry. |
| Embedding dimension | Vector dimension must match the selected embedding model | Fix the MVP contract to `vector(1536)` and store model name/version. Re-embedding is required when the model/dimension changes. |
| Notifications | `delivery_channel=all` has no per-channel delivery table | Keep one notification row for MVP; use `delivery_status` for aggregate status and document per-channel delivery as a post-MVP extension. Add an idempotency key for generated notifications. |
| Concurrency | Mission/report/settings can be edited concurrently | Use EF concurrency tokens: PostgreSQL `xmin` for mission state and integer version columns for reports/settings. |
| Deletion behavior | Default cascade can destroy inspection history | Restrict business FKs by default. Cascade only owned junction/refresh-token rows. Set-null actor references where history must survive account removal. |

## 3. Required field-level additions/edits

### 3.1 Users/RBAC

- `users.normalized_email` and `users.normalized_username`: required, lowercase, unique.
- `users.password_hash`: required, max 512; never returned through DTOs.
- `users.last_login_ip`, `refresh_tokens.ip_address`, `audit_logs.ip_address`: max 45 for IPv4/IPv6.
- `users.failed_login_count >= 0`; `lockout_end_at` is nullable.
- Refresh token `token_hash` and `jwt_id` are required unique values; raw refresh tokens are never stored.
- Audit logs must include `occurred_at`, action, category, request correlation ID, and redacted JSON payloads. Add `correlation_id` for cross-service tracing.
- System settings require a typed JSON value, version, and update actor; secret values must not be stored as plain settings.

### 3.2 Assets

- Add required `organization_id` FK to `assets`.
- `code` is required and unique within an organization, not globally.
- Add `normalized_code` and a composite unique index `(organization_id, normalized_code)`.
- `country_code` is `varchar(2)`, not `CHAR(2)`.
- Require latitude and longitude together; validate ranges.
- Keep `metadata` and `specifications` as JSONB, but do not use them for frequently filtered fields.
- Add `search_vector` plus GIN index and a normal index for `(organization_id, status)`.
- Document/object keys are required, unique and length-limited; validate MIME type and file size in application code and database range checks.
- Lifecycle log is append-only and must preserve the actor/timestamp even if the actor is later deactivated.

### 3.3 Planning and requests

- Plans require at least one asset before activation; application validation enforces this.
- `frequency_interval >= 1`; end date cannot precede start date.
- A schedule must have a valid date range; cancelled/rescheduled statuses require the corresponding reason/reference.
- Notification creation needs an idempotency key to avoid duplicates from scheduler retries.
- Requests use a unique `mission_creation_key`; `requested_completion_date` cannot precede request creation time.
- Request and schedule status changes must be recorded in audit logs.

### 3.4 Missions and telemetry

- `smartdronehub_mission_id` is nullable until SmartDroneHub accepts the request, then unique.
- Add `external_status_code`/`last_synced_at` to preserve integration state without trusting only a display status.
- Telemetry requires unique `(drone_mission_id, sequence_number)` and non-negative sequence numbers.
- Telemetry validates latitude/longitude, battery `0..100`, signal `0..100`, heading `0..360`, and non-negative altitude/speed.
- Mission images require an object key, MIME type, byte size, capture time, and optional capture coordinates. Remove the reverse AI-job FK.
- Flight logs require unique sequence per mission, severity `1..5`, and event timestamp.

### 3.5 Reports, findings, defects, tickets

- A report is one-to-one with an inspection request; report number is unique and generated server-side.
- Report `findings` text remains for narrative context; structured defects belong in `report_findings`/`defects`.
- Bounding-box coordinates must be normalized `0..1`; confidence must be `0..1`.
- Defect number and ticket number are unique, immutable business identifiers.
- Defect/ticket status transitions require actor, timestamp and history rows; invalid transitions are rejected in the application layer.
- Costs/hours are non-negative; `actual_cost` should not be less than zero, but may be greater than estimate.
- Evidence is soft-deletable, but the underlying MinIO object deletion must be an explicit, auditable operation.
- A maintenance ticket must have either a defect or a valid standalone maintenance request context; enforce the supported rule in application validation.

### 3.6 AI services

- AI jobs require exactly one target and one supported job type.
- Job state transitions are controlled (`queued -> processing -> completed|failed|timeout|cancelled`); completed jobs are immutable except operational metadata.
- Retry count must be `0..max_retries`; priority must be `1..10`.
- Store model name/version, latency, token usage and cost only when supplied; never store provider API keys in payloads.
- Knowledge cases need publication state, language, source, and audit fields.
- Embeddings use `vector(1536)`, unique one-to-one with a knowledge case for the current embedding, and an HNSW cosine index after pgvector is enabled.

## 4. Index and constraint baseline

Required before calling the database production-ready:

- Unique: normalized identity, organization+asset code, external mission ID, object keys, business numbers, token hashes/JTIs.
- Filter: organization/status, request status, mission status, defect status, ticket status, notification unread.
- Time series: telemetry `(mission_id, recorded_at)`, flight logs `(mission_id, logged_at)`, audit `(occurred_at)`.
- Search: assets GIN `search_vector`; knowledge embeddings HNSW cosine.
- Checks: coordinate ranges, percentages, confidence, severity, costs, intervals, date ordering, retry bounds.
- Foreign keys: Restrict by default; explicit Cascade/SetNull only where documented.

## 5. Implementation gates

1. Review document approved internally before entity code.
2. Entity/configuration code compiles with zero warnings introduced.
3. Clean PostgreSQL/pgvector container starts with health checks.
4. EF migration applies from an empty database and can be generated as an idempotent script.
5. Schema inspection confirms every table, index, FK, check and concurrency token.
6. Integration tests cover at least: unique asset code per organization, coordinate rejection, soft-delete filtering, idempotent mission key, telemetry duplicate rejection, report version conflict, and vector extension/index creation.

## 6. Scope boundary

This schema supports SmartDroneInspection's business platform. Drone flight control, firmware and hardware remain external to SmartDroneInspection and are accessed through SmartDroneHub integration contracts.

Any field not present in the official functional requirements is included only when it protects integrity, auditability, tenant isolation, integration idempotency, security or operational traceability. Optional future features such as per-channel notification delivery and monthly partitioning remain out of the MVP migration until measured need exists.

## 7. Implementation status

This document is the review baseline. Entity/configuration/migration work must be checked against it module-by-module; the original plan must not be copied blindly.
